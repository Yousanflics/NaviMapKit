## 1. Repository bootstrap

### 1.1 Toolchain and baseline

- Swift 6.x with the current stable Xcode; `Package.swift` at `swift-tools-version: 6.0`, every target on `swiftLanguageModes: [.v6]` (strict concurrency from day one, 02 §5.2).
- Platform baseline **iOS 18+** (raised from 17 on 2026-09-02, while the SDK still has no shipped consumers — the only moment the change costs nothing). `Duration`, `ContinuousClock`, and Swift Testing are all available. macOS support is not promised, but Core/Scene/Offline pull in no UIKit so portability stays open.
- Test framework: Swift Testing (`@Test` / `#expect`).
- Lint and format: pinned SwiftFormat plus strict SwiftLint, version-locked inside this repository.

Package dependency rules:

- `NaviAviationMapKit` depends on `_RuntimeAssembly` and therefore transitively on the default runtime, so one `import NaviAviationMapKit` is enough to render (02 §1.1, rule 4).
- The renderer package appears only in `_PrimaryVectorRuntime`'s target dependencies, pinned to an exact version.
- Examples are standalone Xcode projects (generated by xcodegen) depending on the local path package.

### 1.3 Branch and PR conventions

- `main` is protected; feature branches are `feat/<scope>`; one PR is one reviewable unit.
- Avoid the word "refactor" in PR titles and bodies.
- During `0.x`, minor versions may break API; from `1.0`, SemVer plus the API digester are enforced.
- **Once a commit is pushed to shared `main`, correct it by appending, never by rewriting.** Amending or force-pushing published history invalidates every review anchor others hold on those SHAs; a lease rejection on such a push is the safeguard working, not an obstacle to route around. (History rewriting is legitimate only for a branch no one else has consumed, and then only with explicit agreement.)

## 2. CI (in place from the first commit; part of the P1 exit criteria)

| Job | Content | Blocking |
|---|---|---|
| build | Two stages, because the renderer SDK is iOS-only and the full graph cannot build on a host toolchain: portable targets (Core/Scene/Offline/Testing, all provider-free) use `swift build`; the full graph including `_PrimaryVectorRuntime` uses `xcodebuild -destination 'iOS Simulator'` (Debug + Release) | ✅ |
| test | Same two-stage split: portable test targets via `swift test`; the full graph via `xcodebuild test -destination 'iOS Simulator'`. Swift Testing results appear on the ◇/✔ lines — an XCTest wrapper line reading "Executed 0 tests" is normal, not a failure | ✅ |
| strict-concurrency | Asserts no target in Package.swift has been downgraded from language mode v6 | ✅ |
| provider-isolation | (a) `git grep 'import <renderer>'` results must be a subset of `_PrimaryVectorRuntime/`; (b) `swift symbolgraph-extract` over every public product, asserting zero symbols referencing renderer modules (02 §5.3) | ✅ |
| api-optionals | Symbol-graph / swiftinterface scan: any banned Optional such as `Optional<VerticalCoordinate>` in a public signature fails the build (§5.4-3) | ✅ |
| api-stability | `swift-api-digester` against the previous tag's public surface; a breakage requires an `api-break` label plus a version bump, and every accepted breakage is itemized with a justification in `scripts/api-breakage-allowlist.txt` | ✅ |
| compile-policy | Negative compile tests for type discipline (§5.4-1), pinned to the host toolchain module paths | ✅ |
| time-conversion report | Lists call sites of named cross-meaning conversions as a review checklist attachment (§5.4-2) | ✅ |
| example-build | Builds NavMapExample (from P2); all three examples (from P8) | ✅ |
| lint | SwiftFormat `--lint`, strict SwiftLint, `git diff --check` | ✅ |

Scripts live in `scripts/`: `check-provider-isolation.sh`, `check-symbol-graph.py`, `check-api-stability.sh`, `check-compile-policy.sh`, `report-time-conversions.sh`. The same set runs locally as a pre-push check.

## 3. Consumer integration (out of scope for this repository)

Migration planning for any application that adopts NaviMapKit — inventory of its existing renderer touchpoints, ordering of its feature migrations, and its own release sequencing — belongs to that application's own documentation and issue tracker, not here. This repository is an independent SDK; it defines the API, the guarantees, and the acceptance criteria a consumer can rely on, and deliberately holds no plan, mapping, or schedule for any specific consuming codebase.

What this repository does provide for integrators: the public API and its guarantees (02 §3), the concurrency and isolation contracts (02 §5), the offline activation protocol (02 §7.4), and the testing product (`NaviMapTesting`) for verifying an integration without a live renderer.

## 4. Phase breakdown (exit criteria and rollback points)

> The first milestone that must render is P2's thin vertical slice, not a protocol-only layer. P0 and P1 together are a week-scale effort; lingering in protocol design is not permitted.

**Stage gate (standing rule).** A phase is complete only when all three hold: exit criteria met, cross-verification passed (an independent review of the exact commit, in addition to the primary review), and every resulting fix item closed. The next phase starts only after that.

### P0 — Foundation ADRs

Tasks: ADR-001 (4D spatial model and identity, including the identity/signature split), ADR-002 (capability negotiation and degradation), ADR-003 (surface ownership and content authority).
**Exit:** three ADRs reviewed and accepted, each including a rejected-alternatives section.
**Rollback:** documentation only; revisions are amendments rather than rewrites.

### P1 — Independent package skeleton

Tasks: repository layout (§1.2), Package.swift on language mode v6, every CI job from §2, `NaviMapTesting` (a scriptable fake surface driver plus snapshot builder), and **the ideal example written and frozen** — the ideal call site is the acceptance artifact for the v0 public API (D5), and it is allowed not to compile yet.
**Exit:** green CI on the skeleton; the ideal example frozen by explicit agreement.
**Rollback:** tag `v0.0.1-skeleton`.

### P2 — Thin vertical slice (first rendering milestone)

Tasks: minimal core types; scene snapshot/delta, component protocol, reconciler core; the default surface driver (attach/apply/detach with acknowledgement); basemap and ownship components plus the `NaviMap` view; viewport free/follow, `flushViewport()`, background flush inside a background task, animation-free restore ordered before GPS follow; the example rendering for real.
**Exit:** the example renders and restores its viewport after a process kill; provider-isolation CI green; a 60fps ownship stream with no main-thread I/O (Instruments spot check, recording the **snapshot-rebuild frequency** — frequent delta-buffer overflow shows up as full-snapshot self-healing, so that counter is the tuning signal for the buffer size).
**Rollback:** tag `v0.1.0`.

### P3 — Runtime isolation

Tasks: point query, snapshot, and typed-event channels land in the SDK; the API-stability digester baseline is wired to the first public tag; a real application integration proves the whole public API; provider-family imports are eliminated from the consumer's feature layer.

**Exit criteria (re-ruled 2026-09-01).** Originally stated as "provider-family imports = 0" in the integrating application. That final step structurally required a cross-repository pull request, a path explicitly closed by the repository-independence rule adopted by the repository owner on 2026-09-01 (this repository must carry no coupling to any specific consuming codebase). The criterion is therefore restated as: **provider-family imports reduced to a single remaining integration surface, whose adoption form is a future decision outside this repository, with all three migration sub-batches independently reviewed and closed.** The change of criterion is caused by a change of rule, not by a shortfall in execution; this provenance note preserves the audit chain.

**Rollback:** each sub-batch is independently revertable; SDK tag `v0.2.0`.

### P4 — Declarative reconciler

Scope (re-cut 2026-09-01 under the same independence rule): ① full component-level mount/update/unmount semantics; ② timeline-driven updates evaluated at the represented-time cursor; ③ surface-rebuild replay plus a regression suite covering the historical failure classes, written as **self-contained generic scenarios** that still pin the original failure modes. Retiring a consumer's host-side manual reinstall path is integration work and has been moved out of this plan.
**Exit:** the regression scenarios pass under a single write path; replay is verified after surface rebuild.
**Rollback:** per-batch revert; no feature flags needed inside the SDK.

### P5 — Offline / content runtime

Tasks: the generation manager actor, the SQLite registry, and the directory layout (02 §4.7, §7.4); content families migrated one batch at a time; **failure-path tests written first** (acknowledgement-timeout rollback; kill during `activating` followed by startup reconciliation; staging-orphan cleanup; regional-lease persistence across restart — at least one case each); main-thread contract assertions.
**Exit:** failure-path tests green; no main-thread disk I/O on offline startup (Instruments verification, see §5.5 obligation 2); the legacy tile-source path replaced.
*On that last criterion (recorded 2026-09-01):* it originally meant retiring a consuming application's old path, which the repository-independence rule moved out of scope (§3). It is **replaced, not dropped** — the SDK-side equivalent is that an activated generation directory becomes the provider's content source — so the criterion still has to be met here, by different work.
**Start condition (re-cut 2026-09-01):** a tracing host is **not** required to begin this phase — it is a hard *exit* prerequisite only. P5 may be implemented and dual-reviewed in full while a host is unavailable, but **cannot be closed** until direct Instruments capture is obtained; substitute evidence chains remain refused (§5.5 obligation 2, unchanged). Every P5 batch report carries an explicit standing line recording tracing-host availability ("host unavailable" / "host available, <date>"); a batch report without it is not accepted for review, so the outstanding capture stays a visible to-do instead of fading across batches. The **DEBUG main-thread I/O assertion hook (§5.5 obligation 1) must be the first commit of this phase** — while direct capture is unavailable it is the only standing defence for the main-thread contract, so its priority rises rather than falls.
**Rollback:** each content family behind its own flag; the registry schema is versioned and downgrade-readable.

### P6 — Aviation domain pack

Component design and publication order: **[04 — Aviation domain pack](04-aviation-domain-pack.md)**.

Tasks, in the order that document fixes: (1) the missing Core primitives, each landing as its own item —
`NavigationVolume` with `HorizontalGeometry` and `DataQuality`, then `MovingEntity` — frozen and entered
into the digester baseline before any component consumes them; (2) the mechanism extensions those
components need, each raised and ruled separately from the component that wants it — the
`upsertArea`/`removeArea` base-primitive expansion (ADR-002 §5, on the same conditions as the previous
three), the capability negotiator's degradation path, and a collection scene-element kind for streamed
traffic; (3) the components themselves — airspace and temporary restrictions, then traffic — one per
batch, each extending the frozen example first (D5); (4) airports and procedures as content
generations through the P5 pipeline, which need no new mechanism; (5) the tile-archive content family,
then weather; (6) measurement, selection, and altitude filtering as handle facilities beside

**Exit:** every component published in this phase is reachable from the frozen example; each Core
primitive and mechanism extension it introduced is separately frozen in the digester baseline; the
altitude-filter matrix of 01 §4.3 criterion 9 passes with every `.unknown` cell resolving to visible;
and no safety-relevant depiction degrades without a reported `CapabilityReport` entry.
**Rollback:** additive per batch — a component that has not been published can be withdrawn by
reverting its batch, and a Core primitive already in the digester baseline is removed only through the
recorded API-breakage process.

*Scope re-cut (2026-09-02).* This phase previously read "airspace, airports, procedures, traffic,
weather, routes, measurement, selection, and altitude filtering, migrated one or two components per
batch", with the exit criterion "the domain feature checklist passes in full" and a rollback that
assumed an old implementation to coexist with. Three things were wrong with it, and each was found by
execution rather than by reading. The nine items are **not nine components**: three are content
generations, three are handle facilities, and routes are already published — treating them uniformly
would have built the wrong thing three times over. The primitives they build on were assumed to
exist; `NavigationVolume`, `MovingEntity`, `HorizontalGeometry` and `DataQuality` have no declaration
in `Sources`, so the phase silently contained a set of unscheduled Core items. And the rollback
described coexisting old and new implementations, which no longer applies to an independent SDK with
no legacy path to keep alongside. **Replaced, not dropped**, on the same principle as the P5
tile-source criterion and the P7 re-cut above: the obligation stays, restated as work this repository
can actually sequence and verify.

### P7 — Integration sufficiency

Tasks: demonstrate, without a consuming application, that the public surface is sufficient for an integrator to
hold zero direct renderer imports and to keep map responsibilities out of their own coordinators — the scenarios
of 01 §4.3 (criteria 1, 2, 11) expressed against `NaviMapTesting`'s fake driver, plus the gaps that exercise
reveals closed in the public API.
**Exit:** those scenarios run green against the fake driver with no renderer import anywhere in their sources
(the provider-isolation job already proves the SDK side; this proves the *integrator* side is reachable), and
`NaviMapTesting` ships whatever they needed.
**Rollback:** additive only — the phase adds test scenarios and, where a gap is found, public API.

*Scope re-cut (2026-09-02, decided by the repository owner).* This phase previously read "integrating
applications reach zero direct renderer imports", with its exit tied to auditing a consuming codebase. The
repository-independence rule (§3) put any specific consumer's migration outside this repository, which left the
phase unachievable as written — listed in the sequence but with a criterion nobody here could meet. It is
**replaced, not dropped**, on the same principle applied to the P5 tile-source criterion: the obligation stays,
restated as something this repository can verify. The distinction matters because the original criterion was
never really about a consumer's diff — it was about whether *our* public surface makes that outcome possible.
A consumer failing it would have been evidence about our API, so the API is what the phase should test.

### P8 — Maritime / UAS proof

Tasks: a maritime example (AIS moving entities, CPA/TCPA as internal draft, chart-datum vertical reference) and a UAS example (mission waypoints, 3D inclusion/exclusion geofence volumes, AGL terrain query stub).
**Exit:** both examples build against the same core and runtime as the aviation example; the core contains no aviation-specific types (compile audit).
**Rollback:** additive only.

## 5. Test strategy

**Wait for the condition you assert.** An asynchronous test that drains until *X* and then asserts *Y*
is only correct when *X* implies *Y*; where it does not, the test passes or fails on timing and will
eventually do both. One instance, found as a one-in-seven flake rather than by reading: a case waited
until content health became `fresh` and then asserted the content source was bound. Health is settled
by the refresh that follows activation, while binding lands on a later publish — two events with no
ordering between them, so the assertion was racing a condition that never guaranteed it. The remedy is
not a longer timeout or a retry; it is to drain on the bound source itself, so the wait and the claim
are the same fact. This is the testing form of the rule that a gate must assert what it actually
examined (§5.4): a proxy that usually coincides with the thing you care about is not the thing you
care about, and the gap shows up as flakiness rather than as a failure anyone can read.

### 5.1 Layers

| Layer | Tooling | Coverage |
|---|---|---|
| Core values and pure functions | Swift Testing, parameterized | Type semantics, signature derivation, time model, unknown propagation |
| Reconciler | FakeSurfaceDriver | mount/update/unmount matrix, epoch rejection, rebuild replay, historical failure-class regressions |
| Offline state machine | In-memory FS + real SQLite + scripted driver acknowledgements | The full failure-path set from §4-P5 |
| Vertical-slice integration | A small number of example UI tests | Rendering, viewport restore, selection callbacks |

### 5.2 Replay harness (NaviMapTesting)

Records a delta stream plus driver acknowledgement timing as JSON and replays it. It verifies reconciler behavioural equivalence across changes and reproduces concurrency-timing defects deterministically.

### 5.3 Conservative-visibility test matrix (implements acceptance criterion 9)

A parameterized test enumerates {`VerticalCoordinate.unknown`, `DataFreshness.unknown`, `DataQuality.unknown`, expired validity} × {capability satisfied, degraded, incompatible} × {altitude filter on/off, timeline cursor live/replay}. It asserts that in every combination a safety component (airspace, hazard, restricted volume) evaluates to {visible} or {explicit incompatible report} and **never** to silent hiding. The matrix is generated from the dimensions, so a new unknown dimension enters it automatically.

### 5.4 Enforcement mechanisms for type discipline

Each rule uses a mechanism that can actually enforce it, rather than pushing everything into `-typecheck`:

**Every gate carries a positive control.** A gate is only evidence if it can be shown to fail on input that should fail; "the tree is green" is compatible with the gate checking nothing at all. Each entry below therefore names both a known-bad input it must flag and a known-good input it must pass, and the self-check runs both. This is not hypothetical: the default-argument gate (rule 5) first reported green because its parameter-list regex truncated at a parenthesised type (`(any ContentFileSystem)?`), so every parameter after that one — including a violating default — was never examined. It was caught by a human reading the source, not by the gate. A known-bad list is what converts a green gate from an assertion into evidence.

**Two further properties, both learned the same way.**

- **The standing self-check may not depend on git history.** It runs on checked-in fixtures — a must-fail and a must-pass file, as `Tests/CompilePolicyTests/Fixtures/` already does for rule 1 — so that the three standing conditions (fixture red, fixture green, tree clean) survive any rewrite. Backtesting a gate against the commits of past incidents is worth doing once and recording as text in the evidence note: it establishes that the gate catches those incidents, and that conclusion stays true permanently without the objects surviving. Wiring the standing check to those SHAs does not, because a rebase or a garbage collection removes the positive control while the gate keeps reporting green.
- **A gate must assert a lower bound on what it examined, and a missing path is an error.** Reporting the count is not enough; the count must be checked. Measured on the default-argument gate: pointing it at a directory with no main-actor types, *and at a path that does not exist at all*, both printed "0 main-actor types checked" and exited zero. A renamed or split source directory therefore turns the gate off silently. Note that the fixtures do not cover this: they live at their own path, so the self-check still passes while the production scan examines nothing. Registering the expected set (names, not just a number) makes the failure name what went missing.
- **A gate may not translate "the operation failed" into "there is nothing to do."** A failure must be red; a benign state may only be established by positive evidence. The api-stability gate previously decided "this module has no baseline, so it must be new" by observing that the baseline dump *failed* — which means a dump failing for any unrelated reason was silently reclassified as benign, and the gate could report green having compared nothing. It now decides newness from `git ls-tree` and treats every dump failure as red. The same shape appeared in the acceptance example, whose `catch` read a `stage` error as "probably installed on a previous launch"; it is now a distinguishable public signal instead (02 §4.4). The rule generalises: whenever code infers a benign condition from an error, the inference is only as narrow as the error is specific, and errors are rarely that specific.
- **A gate that exempts itself must prove the exemption is empty.** Every scanning gate excludes its own source, or it would match its own patterns. That exclusion is a permanent blind spot unless the gate also asserts that its own file contains none of what it forbids. The independence gate was written with the brand terms assembled from fragments *and still* carried the channel name and two literal CJK characters — invisible precisely because the file was exempt. A self-check added afterwards flagged them within a minute, before any reviewer read the file. The rule generalises past scanning: wherever a mechanism is excused from its own requirement for a good reason, the excuse needs its own assertion, because nothing else will ever look there.
- **Confirm the instrument before believing the measurement.** The three rules above constrain the gate; this one constrains whoever cites a gate as evidence. A non-zero exit does not establish that the assertion held, and a zero does not establish that it passed: the command may not exist, the path may be wrong, or the status may belong to something else entirely. Four practices follow. **(1)** Take the exit status from the process under test; where a pipe is unavoidable, read `PIPESTATUS[0]` rather than the last stage. **(2)** Pair every expected red with its diagnostic text — a correct exit code with the wrong message is a failed measurement, not a satisfied assertion. **(3)** Pair every expected green with its denominator line ("N types checked", "N modules compared") and check N against the registration; without this a person can honestly cite a vacuous green. **(4)** Prefer the tool's own `--self-test` over an ad-hoc harness; when a modified copy is unavoidable, first run the *unmodified* copy and confirm it is green, which proves the harness works before its red is believed. Four instances arose in a single day of this work — a missing `timeout` on macOS returning 127, an exit status swallowed by a pipe reading as 0, a self-locating script copied outside its tree returning 128, and an existence survey run with `git grep -E '\bType\b'`, where git's ERE has no `\b`, so **every** type came back absent including the ones known to be present. That last one is the most instructive: its output was a plausible, internally consistent list of "nothing exists" that looked exactly like a real finding, and two separate reviewers hit it. It was caught only because one of them checked a known-present type first — which is practice (2) above applied to a survey rather than to a gate. A fifth followed the same week: a case-insensitive grep for a reviewer's name matched `RenderColor.alpha` and `fillOpacity = style.fill.alpha`, reporting seven independence violations that did not exist. False red and false green are the same failure — one convicts correct code, the other acquits broken code — and both come from a matcher nobody checked first. A sixth instance is specific to prose and defeats the natural way of checking a document: **a line-based search can prove presence but not absence.** A reviewer confirmed a sentence had been deleted by grepping for it and getting no hits — the sentence was still there, split across a line break, and `git grep` matches within lines. The tool was not broken; it was asked a question it cannot answer, and the same search was sound for the short single-line phrases it checked elsewhere. To show a phrase is gone from prose, join the lines first (`tr '\n' ' '`) and search that. This one bites immediately: the edit adding this very sentence failed its first attempt because its anchor also spanned a line break. In short: **establish that the instrument is alive before concluding anything about the subject** — the same discipline as running a gate's `--self-test` before its scan, applied on the human side. A false red and a false green are one failure wearing different clothes: the first convicts correct code, the second acquits broken code, and both come from an unverified instrument.

- **Confirm which tree you are editing, not just which question you are asking.** The rule above
  constrains the instrument; this one constrains the subject. A search can be sound, its pattern
  correct and its result honest, and the finding still be worthless because the working copy answered
  for a different tree than the one under discussion. Measured twice in this work. A reviewer read a
  clean implementation out of a checked-out tree and nearly reported a finding false; the clean code
  was an uncommitted local fix, and the reviewed commit contained the defect. Later, the same shape
  with the branches reversed: version anchors in these documents were rewritten while a feature branch
  was checked out, though the documentation line lived on `main` and the two copies of the file
  differed by two hundred lines. The anchor count happened to match on both branches, so the check
  reported success — truthfully, about the wrong file. Publishing that edit would have reverted the
  documentation silently. Neither case produced an error, a conflict, or any other outward sign; both
  were arithmetic performed on the wrong operand. The practice is cheap: before editing or citing,
  reconcile `git rev-parse HEAD` against the commit under discussion, or work only in a worktree
  created from that exact SHA. A tree checked out for one purpose does not announce that it is the
  wrong tree for another.

1. **Implicit time mixing → negative compile tests** (`CompilePolicyTests`, `swiftc -typecheck` importing this package): assert that implicit flow from `InstalledAt` to `ObservedAt` (direct assignment, direct argument passing) fails to compile with the expected diagnostic. Explicit non-goal: a conversion routed through `.instant` **does** compile — the protection is "implicit blocked, explicit funnelled into a named init", not a prohibition (02 §4.2). A positive must-compile fixture guards against hollow green from a broken include path.
2. **Auditability of named downgrade conversions → CI grep report**: `scripts/report-time-conversions.sh` lists every call site of the named conversion initializers as a review checklist attachment; growth in the count must be justified in the PR description.
2.5 **Known blind spot in the API-stability gate: it does not report a newly public top-level type.**
   Measured 2026-09-03 — a batch that made `TileGrid` `public` produced digester reports whose
   added/removed line counts were **identical, module for module**, to the parent commit's. The gate
   compares declarations it can pair against a baseline and is therefore reliable for *changes* to
   existing public API, which is what it was built for; a brand-new top-level type has no counterpart
   to pair with and passes unremarked. So "api-stability OK" is evidence that nothing existing broke,
   **not** that nothing new was published, and the public surface has to be guarded by reading the diff
   in review. Recording it here rather than as a review habit, because a habit that lives only in
   reviewers' heads is what this whole section exists to replace. It was found by a reviewer noticing
   that a public addition they had spotted by eye was absent from the report — which is the denominator
   rule (§5.4 above) applied to a gate whose denominator is "declarations that exist on both sides".

3. **No banned Optionals in the public API → symbol-graph audit**: such code is always legal to `-typecheck`, so a negative compile test proves nothing; `check-symbol-graph.py` scans public declarations instead and fails on `Optional<VerticalCoordinate>` (or `VerticalCoordinate?` in the interface). This is the `api-optionals` job alongside provider-isolation in §2.
4. **No renderer imports outside the internal runtime → enforced by the provider-isolation job** (grep plus symbol graph); not duplicated as a compile test, because a bare `-typecheck` would fail hollowly for lack of search paths.
5. **No file-system-touching evaluation in a default argument of a main-actor-constructed type → CI grep**. A default argument is evaluated at the *call site*, and for these types the call site is view construction on the main thread. Anything there that looks like "just computing a path" therefore runs on the main thread, and the DEBUG main-thread I/O hook cannot see it (§5.5): Foundation issues the syscall inside path handling, never reaching an `assertOffMainThread` call site. The rule is: **a default argument of a main-actor-constructed type performs no evaluation at all; the default is a constant marker or `nil`, resolved on first use on the I/O queue or the preparation actor.** The check is a *positive whitelist* over the default-argument expression and, where that expression names a static, over that static's definition body: **only literals, `nil`, and enum cases are permitted; every call expression fails, construction included**. Constructing a type is not exempt — the gate reads the default-argument site and the bodies of statics, not the body of an arbitrary `init`, so allowing `SomeType()` would let a type that acquires file access in its initializer pass unnoticed. The cost of the strict reading is a `nil` default plus a fallback in the initializer body, which is cheap and keeps the gate decidable without whole-program analysis. A blacklist is unusable here — four distinct Foundation entry points have been found and each of the first three was believed to be the last (see §5.5), so named APIs serve only as hint text, never as the verdict. The check targets definition bodies rather than call sites because that is where every observed instance hid: a line reading `init(store: Store = .default)` contains nothing suspicious while the syscall sits inside `.default`'s body. Registering a new default argument is itself part of the check.
6. **No consumer, organisation, ticket, or CJK trace anywhere in the repository → `check-repository-independence.sh`**. This rule was previously enforced by reviewers running greps by hand, which is to say it had no mechanism at all — every "independence clean" in review was a person remembering to look, and one of those greps produced a false red of its own. The gate scans **every tracked file** (`docs/` included; excluding it would only leave a hole) and the **commit messages of new commits**, since the rule covers those too and nothing checked them. Two properties are specific to this gate. Its scope is deliberately not narrowed: the uncovered surfaces that prompted it were `scripts/*.txt`, `.github/`, `README.md` and `Package.swift`, none of which any earlier check reached. And its **known-bad input cannot be committed** — a fixture containing the forbidden terms would violate the rule it guards and be flagged by this very scan — so the self-test assembles that input from fragments at run time and only the known-good fixture is stored. Commit-message coverage is honestly bounded: it examines new commits, preventing re-entry rather than proving history clean, which a single earlier rewrite already handled.

### 5.5 Performance guards

- A benchmark on reconciler diff time under 60fps ownship updates, with the threshold enforced in CI.
- Startup path: two mechanisms with **different coverage**, neither sufficient alone. The DEBUG main-thread I/O assertion hook is an *opt-in call-site marker*: it fires only where `assertOffMainThread` was written, so it enforces discipline at annotated sites and cannot detect disk access at an unannotated site or a syscall issued inside Foundation. Device tracing enumerates syscalls regardless of origin and is therefore the only mechanism that can substantiate "zero main-thread disk I/O" as stated (P2/P5 exit criteria).
- **Two standing obligations recorded at the close of P2:**
  1. **The DEBUG main-thread I/O assertion hook lands no later than the start of P5.** P2's no-main-thread-I/O criterion passed on an evidence chain of sustained 60fps plus a constructive argument about the only file-I/O surface in scope (direct Instruments capture was unavailable due to a host-environment fault). The assertion hook is the durable *call-site* mechanism and may not be deferred again — but see the 2026-09-02 record below for what it does not cover.
  2. **Direct Instruments capture is retried in a different environment at P3** (an environment fault is not an exemption). For P5 — tile archives, SQLite, and the registry, where the real risk of this criterion lives — Instruments verification remains a **hard exit criterion** with no substitute evidence chain accepted. *P3 retry ruling (2026-08-31): procedurally complete, evidentially unmet* — after changing the target application the tracing tool could attach and start recording but never wrote to disk, isolating the fault to the host runtime. The obligation rolls into P5 unchanged, with an added precondition: **a working tracing host (a wired device or a second Mac) must exist** — *re-cut 2026-09-01 (design review ruling): this is a hard prerequisite for **closing** P5, not for starting it.* Implementation and dual review may proceed without a host; the phase simply cannot be closed until direct capture is obtained, and no substitute evidence chain is accepted. **Host status: available from 2026-09-02** (a wired device is connected), so the capture is now an executable closing task rather than a blocked one; the criterion itself is unchanged and still admits no substitute evidence.

  **Record — 2026-09-02, first device capture (why obligation 2 admits no substitute).** The first tier-1 capture (full `fs-syscall` enumeration filtered to the example app's pid and main thread id) found exactly two main-thread file syscalls in SDK code, and the assertion hook was blind to both: `FileManager.urls(for:in:)` and an `appendingPathComponent` without an `isDirectory:` label each issue an implicit `stat64`/`lstat64` from inside Foundation, never reaching an `assertOffMainThread` call site. The hook reported zero violations in the same run. This is the concrete demonstration that a green hook is *not* evidence for this criterion: it constrains the call sites it annotates, while the criterion quantifies over all syscalls. Both sites were fixed by computing default paths as strings and labelling every `appendingPathComponent`; the corresponding audit found the remaining unlabelled uses in `Sources` to be on `ContentPreparationActor` or in test fakes, i.e. off the main thread. Nothing structurally prevents a new main-actor site from reintroducing the class, and no cheap static check distinguishes main-actor call sites reliably — so the per-milestone device capture, not the hook, remains the detector of record.

  **Record — 2026-09-02, the class is larger than the first two sites.** A second capture after those fixes still showed two main-thread stats from SDK code, with a *different* origin: `URL(fileURLWithPath:)` stats during path standardization. Three distinct Foundation entry points in this class are now known — `FileManager.urls(for:in:)`, `appendingPathComponent` without an `isDirectory:` label, and `URL(fileURLWithPath:)` — and there is no reason to believe the list is complete. The rule was therefore written against the *location* rather than the API set (§5.4 rule 5): on the main thread a path is a `String`; `URL` construction happens off it. The amplifier in every incident was the same — a **default argument** on a main-actor-constructed type, evaluated at the view-construction call site.

  **Record — 2026-09-02, third capture: the fourth entry point invalidates the first corollary.** After moving to pure string concatenation, two main-thread stats remained, now under `NSHomeDirectory()` itself: resolving the home directory stats. So the rule "a path is a `String` on the main thread" was wrong — *producing* the string is already file-system access. The corollary is now the stronger one: a default argument carries an inert marker and the whole evaluation is deferred off the main thread. This is the fourth distinct Foundation entry point in the class; each of the previous three was believed to be the last one, which is the reason the rule is stated against location and the device capture remains the detector of record.
